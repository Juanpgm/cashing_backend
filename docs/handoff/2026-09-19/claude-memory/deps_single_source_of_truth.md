**What:** Se consolidaron las dependencias del backend a UNA sola fuente de verdad, eliminando el drift que rompía builds/verify (ver [[bugfix-deps-fastapi-mcp]]).

**Decisión:**
- `pyproject.toml` = única fuente editable a mano. Runtime en `[project.dependencies]`, tooling en `[dependency-groups].dev`, `[tool.uv] package = false` (es app, no librería).
- `uv.lock`, `requirements.txt`, `requirements-dev.txt` = **GENERADOS**. Nunca editar a mano (tienen header "autogenerated by uv").
- Flujo: editás deps en `pyproject.toml` → `make lock` (corre `uv lock` + `uv export` de ambos requirements).
- `make setup` ahora usa `uv sync` (lee pyproject+lock directo).

**Consumidores (ninguno roto):** Dockerfile/Dockerfile.dev siguen con `pip install -r requirements*.txt` (ahora generados, pinneados, con markers de plataforma → seguros para Docker Linux aunque se generen en Windows). Railway igual.

**Where:** `cashing-backend/pyproject.toml`, `Makefile` (target `lock`, `setup`→uv sync), `requirements.txt`/`requirements-dev.txt` (generados), `CLAUDE.md` (regla documentada).

**Learned:**
- `uv export --no-hashes --no-default-groups --no-emit-project` → requirements.txt (runtime); sin `--no-default-groups` → requirements-dev.txt (runtime+dev).
- `--no-hashes` mantiene el comportamiento pip actual (sin `--require-hashes`); `--no-emit-project` evita la línea `-e .`.
- `package=false` es lo que permite `uv lock`/`uv sync` sin `[build-system]`.
- GOTCHA cerrado: `firebase-admin` (auth core, usado en app/core/firebase_admin.py) estaba SOLO en pyproject, no en el viejo requirements.txt → el Docker de prod nunca lo instalaba (import lazy, no crasheaba al arranque pero sí en auth Firebase). La consolidación lo mete al build.
- Regla: al agregar/cambiar una dep, editar SOLO pyproject.toml y correr `make lock`. Nunca tocar requirements*.txt.
